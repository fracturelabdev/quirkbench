# quirkbench

**ローカル LLM の「癖」を測る。** 総合スコアで順位をつけるのではなく、
**そのモデルが何を得意とし、何を苦手とし、どう失敗するか**の輪郭を描く。

「発想や提案は良いが、コードは弱い」— そういう傾向を、手元のモデルで、自分の機材で測る。

対象は **Ollama で動くモデルのみ**。これは制約ではなく前提条件で、
課金もレート制限も無いからこそ**同じ問題を seed を変えて何度も回し、
ばらつきそのものを癖として測れる**。

> **ステータス: v0.1.0.dev0。** **全 8 次元**の採点、生成・再開、プロファイル表と
> 比較ビューの出力までが動く。**下に手元で回した実データがある。**
> 次元あたりのケース数を増やすのが次の課題。

---

## 測らないもの

**先に書く。ここを誤解したまま数字を読まれるのが一番まずい。**

- **「発想の質」は測っていない。** `ideate` 次元が出すのは
  **制約内多様性 (constrained diversity)** — 指定件数を守ったか、お題から外れていないか、
  想定観点をどれだけ含むか、案同士がどれだけ重複していないか。
  **「良いアイデアかどうか」は測れない。** 生の出力を全件保存して人が読めるようにしてあるので、
  質の判断はそちらで行う。
  スコアは `valid_rate × coverage × diversity` の**乗算**で、どれか 1 つが 0 なら 0 になる —
  支離滅裂な出力ほど案同士が散らばるので、多様性だけを見ると**壊れたモデルが最高得点を取る**
- **LLM に採点させない。** 手元で動く最大級のモデルでも、被験モデルと同程度かそれ以下の能力しかない。
  同じモデルファミリなら誤差が相関し、自分に似た出力を高く評価する
- **他人の環境の再現ではない。** 量子化・`num_ctx`・マシンの負荷で数字は動く。
  ここで出るのは**あなたの手元での**プロファイルであって、モデルの絶対的な性能ではない

## 分かっている限界

**設計上の限界を先に書く。**

- **モデル数が少ないとプロファイルが不安定になる。** スコアは
  「ケースごとに全モデルの平均を引いた残差」で出すので、比較対象が少ないほど推定が甘くなる。
  同じファミリのモデルばかりだと誤差も相関する。**モデルを足すほど安定する**
- **生成コードのメモリ使用量は制限できない。** macOS では
  `RLIMIT_AS` / `RLIMIT_DATA` / `RLIMIT_STACK` のいずれも設定できず、Python が
  `ValueError: current limit exceeds maximum limit` を投げる（この Mac で実測）。
  CPU 時間と実時間の二重で止める設計だが、**メモリ暴走に対する上限は無い**
- **生成コードが非決定的だと、判定の再現性を保証できない。** 時刻に依存する、
  浮動小数の演算順序に依存するコードは、実行のたびに通ったり落ちたりしうる。
  実行結果はコード内容単位でキャッシュするので**初回の判定が安定して返る**が、
  それは**誤っていても安定する**という意味でもある。二重実行による検出は入れていない
  （全ケースのコストが 2 倍になる）
- **`ideate` の脱線判定は、短い固有名詞で誤爆する。** 案とお題の埋め込み類似度で
  足切りしているが、実測で**良質な店名 `すずらん亭`（0.3196）が、無関係な出力
  `塾の音のすばやさ`（0.3261）より低く**出た。分離できていない（閾値 0.35）。
  誤爆で落ちたぶんは `valid_rate` と `valid_rate_morph`（足切り前）の差として
  `scores.jsonl` に残るので、**どれだけ削られたかは後から読める**。
  現状 **7b の `ideate` は過小評価**されている
- **`ideate` の絶対値は他の次元と直接比べられない。** 3 つの積なので上限に届かず、
  **手元の実測で観測された最大は 0.279**（他の次元は 1.000 に届く）。`instruct` の 0〜1 とは尺度が違う
- **`longctx` は `num_ctx` が足りないと成立しない。** プロンプトが収まらないと
  ollama は**エラーも警告も出さずに切り詰める**。手元の実測では 7,821 文字を
  `num_ctx` 4096 に投げると 2,050 トークンしか入らず、モデルは
  「文中に記述はありません」と答えた。そのまま採点すると
  「長文脈で事実を保持できない」という結論が出るが、**実際には事実を渡していない**。
  `qb lint-cases` が静的に、`qb run` が実測値（`prompt_eval_count`）で二重に止める
- **「この次元に弱い」と「このケースに弱い」は、ケースを足すまで分けられない。**
  `z` は識別力のあるケースだけから計算するので、観測が少ないほどその中の 1 件で決まる。
  手元の実測では、`instruct` の問題を 1 種類から 2 種類に増やしただけで
  **同じ 2 モデルの勝敗が問題ごとに入れ替わった**。
  **`qb stability` がこのぶれを数値で出す** — ケースを 1 件抜いて集計し直し、
  `z` がどこまで動くかを見る。新しい生成はしない。
  ただし**測れるようになるだけで、直るわけではない**。直すにはケースを足すしかない
- **ケースは「件数」ではなく「問題の種類」で数える必要がある。**
  同じ問題を日本語と英語で聞いても、独立した観測は 1 件しかない。
  ケース定義の `task` がその単位で、`qb stability` はこちらを数える
- **計測中に他のプロセスが GPU やディスクを使うと数字が汚れる。** 特に `load_duration` に効く
- **仮名の無い短い日本語は言語判定できない。** 「珈琲小径」のような全漢字の店名を並べると
  `unknown` になり、`wrong_language` / `zh_leak` の母数から外れる。
  **判定不能を「別言語だった」と数えない**ためだが、そのぶん日本語運用の母数は減る

## 必要なもの

- Python 3.11 以上と [uv](https://docs.astral.sh/uv/)
- [Ollama](https://ollama.com/) が動いていること（`ollama serve`）
- 測りたいモデルが `ollama pull` 済みであること
- `ideate` 次元を採点するなら **埋め込みモデル**も要る（既定 `bge-m3`）

```sh
ollama pull bge-m3
```

```sh
uv sync
```

## 使い方

```sh
# 生成を実行する
uv run qb run --models qwen2.5:0.5b,qwen2.5:1.5b --repeats 5

# 進捗を見る
uv run qb status
```

**中断してよい。** `Ctrl-C` で止めても、同じ `--run` 名で再実行すれば続きから再開する。
全次元を複数モデルで回すと数時間かかるので、そういう作り方にしてある。

```sh
# 次元やケースで絞る
uv run qb run --models qwen2.5:7b --dims instruct,ideate
uv run qb run --models qwen2.5:7b --ids instruct-json-profile-ja
```

採点は生成と別のコマンドに分けてある。**採点は追記のみで、生成を書き換えない。**
期待値や schema を直したら `qb score` をもう一度回せばよく、数時間かけた生成は残る。

```sh
# プロファイル表と比較ビューを出す
uv run qb report --run main

# 結論がケースの選び方に依存していないかを見る（新しい生成はしない）
uv run qb stability --run main

# ケース定義のゲート（粒度・timeout・参照解）
uv run qb lint-cases

# 生成済みの応答を採点する
uv run qb score --run main

# 埋め込みモデルを替える（ideate 次元でのみ使う）
uv run qb score --run main --embed-model nomic-embed-text
```

## 開発

```sh
uv run pytest -q                       # テスト
uv run pytest --cov=src/quirkbench     # カバレッジ
uv run ruff check src tests tools      # lint
uv run ruff format src tests tools     # 整形
uv run mypy                            # 型
uv run python tools/mutate.py          # ミューテーション
```

これらは `.github/workflows/checks.yml` で機械的に回る。**手で叩く前提の検査は、
やったことがあるだけでいずれ静かに腐る** — 実際このリポジトリでも、型チェックを
一度も掛けていなかったことが後から見つかった。ollama は CI に無いので、
回るのは生成を伴わない検査だけ。実モデルでの計測は手元で行う。

`tools/mutate.py` は**安全策を 1 つずつ無効化して、テストが落ちることを確かめる**。
カバレッジは「その行を通ったか」しか見ないので、ガードが実際に呼ばれているかは別に測る。
実際、行カバレッジ 100% のファイルで 1 件のガードが無防備だったことがある。
**全部落ちるのが正常**で、生き残りが出たらテストを足すか、そのガードが冗長なら消す。

## ケースの書き方

ケースは `cases/<次元>/*.yaml` に宣言的に置く。コードには埋めない。

```yaml
id: instruct-json-profile-ja
dim: instruct
lang: ja
task: json-profile               # 独立な観測の単位。ja/en の対訳は同じ task
pair: instruct-json-profile-en   # 対訳。日英の差分から「日本語だと落ちるか」を出す

prompt: |
  次の人物紹介から、名前・年齢・職業を抜き出して JSON で出力してください。
  ...

options:
  num_predict: 256

failure:            # どの失敗型を適用するかの宣言。書かれていない型は判定しない
  format: json
  extract: fenced_or_first_object
  language: none    # JSON は言語を持たないので言語判定を適用しない
  min_tokens: 4

score:
  kind: json_schema
  schema: {...}
  expect:           # schema を満たしたうえで値まで合っているか（部分点）
    name: 田中一郎
    age: 42
```

**`failure` に書いていない型は集計の母数に入らない。** これは意図的で、
判定手続きの無い型を一律に適用すると、**モデルの癖ではなく判定器の癖**を測ることになる。

**ケースは読み込み時に検証され、通らないものは起動時に落ちる。** たとえば
`failure.max_tokens` に `options.num_predict` 以上の値を書くと拒否される —
先に `truncated` になるので `overlong` が原理的に発火せず、**母数だけ増えて分子が常に 0** になる。
長さ制約は `max_chars` で書くか `num_predict` を上げる。
（この検証は、当時あった同梱ケース 3 件すべてがこの誤りを踏んでいたのを見つけて足した）

### `task` — ケースの数と観測の数は違う

**同じ問題を日本語と英語で聞いても、独立な観測は 1 件しかない。**
`task` はその単位を明示するもので、`id` の命名規則から推測させない。
`qb stability` はこれを使って「この次元に観測が何件あるか」を出す。

`ja` と `en` の対は**必ず同じ `task`** にする（`qb lint-cases` が検査する）。

### 難度は書く前に測る

**思いついた難度のまま書くと floor か ceiling になる。**
どちらも「識別力なし」として集計から外れるので、
**930 生成を回した後に無駄だったと分かる**（実際にやった）。

候補を複数書いて、1 反復だけ回してから採る。

```bash
qb run    --run probe --ids <候補の id> --repeats 1
qb score  --run probe
qb report --run probe    # 「識別力なし」と出たら捨てる
```

全員が解ける問題も、誰も解けない問題も、モデルの違いを何も語らない。

## 測る次元

| 次元 | 問い方 | 採点 |
|---|---|---|
| `instruct` | 形式制約つきの依頼（schema / 列挙値 / 件数） | schema 検証 × 期待値の一致率 |
| `code-gen` | 関数を書かせる | サンドボックスで実行（`pass@1`） |
| `code-fix` | 壊れた関数を直させる | 同上 |
| `code-read` | バグのある行番号を答えさせる | 正規化後の完全一致 |
| `extract` | 文章 → JSON | **キー単位の一致率**（構造の門は置かない） |
| `reason` | 答えが一意な数値問題 | **最後の数値**を採り、絶対許容差で比較 |
| `longctx` | 長文に事実を埋めて問う（針の位置を 3 通り） | 答えを含むか |
| `ideate` | k 個の案を出させる | 制約内多様性（下記） |

**`reason` が「最後の数値」を採るのは、素の数値だけを正解にすると
測るのが算数ではなく指示追従になるから。** 指示追従は `instruct` が測る次元で、
両方に入れると同じものを二重に数える。素の数値だったかは `bare_answer` に残る。

**`extract` が余分なキーを減点しないのも同じ理由。** 拾えたかを測る次元であって、
余計を出さないかを測る次元ではない。

## `code-gen` — 生成コードを実行して測る

**`code-gen` 次元は macOS 専用**（`sandbox-exec` が要る）。スコアは **0 か 1**（all-or-nothing）で、
反復の平均が `pass@1` になる。

```sh
uv run qb run   --models qwen2.5:1.5b,qwen2.5:7b --dims code-gen --run s3
uv run qb score --run s3 --dims code-gen
```

採点のたびに**隔離が生きているかを自己診断**し、1 本でも期待どおりでなければ**採点を拒否**する。
さらに**参照解が自分のテストを通ることをケースごとに確かめる**（陽性対照）— 陰性カナリアだけだと、
隔離が過剰に厳しくなる方向に壊れたときに**全モデルが 0 点になったものを
「このモデル群はコードが書けない」というプロファイルとして出してしまう**。

実行結果は `exec_cache.jsonl` にコード内容単位でキャッシュされる。
**同じコードが別の生成に現れるのは常態**で、手元の実測（run `s9`）では
`code-gen` と `code-fix` の **240 生成に対してサンドボックスの起動は 156 回**、
82 回はキャッシュに当たった。
**採点をやり直してもサンドボックスは起動しない** — 起動するのはコードかテストか実行環境が変わったときだけ。
実測では、採点行を空にして **930 生成を採点し直したときの起動が 0 回**（キャッシュヒット 238 回）で、
**930 件すべての採点値が元と一致した。**

## `ideate` — 「発想」ではなく制約内多様性を測る

**採点に埋め込みモデルが要る**（既定 `bge-m3`）。スコアは 3 つの積で出す。

```
ideate = valid_rate × coverage × diversity
```

| 因子 | 中身 |
|---|---|
| `valid_rate` | 案として成立した件数 ÷ **要求件数**。産出件数で割らない — 1 案だけ返して満点が取れてしまう |
| `coverage` | 想定観点のグループをいくつ含んだか |
| `diversity` | 案同士の埋め込み距離の平均。1 案以下なら 0 |

**成立判定は 2 段。** 第 1 段は形態（長さ・文字種）で決定的。第 2 段はお題との埋め込み類似度で、
**こちらは誤爆する**（「分かっている限界」参照）。第 1 段だけの値も `valid_rate_morph` として
併記するので、**第 2 段がどれだけ削ったかは後から読める**。

```sh
uv run qb run   --models qwen2.5:1.5b,qwen2.5:7b --dims ideate --run s4
uv run qb score --run s4 --dims ideate
```

埋め込みは `embeddings.jsonl` に本文単位でキャッシュされる。
**採点をやり直しても再計算しない** — 手元の実測（run `s9`）では、
**930 生成を採点し直したときの埋め込み計算は 0 本**（キャッシュヒット 700 本）だった。

## 出力

`runs/<run 名>/` に追記される。**一度書いた生成は書き換えない。**

| ファイル | 中身 |
|---|---|
| `generations.jsonl` | 生成 1 件 1 行。生の応答と所要時間。**不変** |
| `prompts.jsonl` | プロンプト本文（重複排除） |
| `scores.jsonl` | 採点結果。再採点は追記のみで、過去の採点も残る |
| `exec_cache.jsonl` | 生成コードの実行結果。コード内容単位（`code-gen` のみ） |
| `embeddings.jsonl` | 埋め込みベクトル。本文単位（`ideate` のみ・1 行あたり約 14KB） |
| `reports/<run>/report.md` | プロファイル表（`qb report` が出す） |
| `reports/<run>/compare.md` | 同一 seed の生出力を並べた比較ビュー |
| `reports/<run>/stability.md` | ケースを 1 件抜いたときに `z` がどこまで動くか（`qb stability`） |
| `meta.json` | モデルの digest、Ollama のバージョン、マシンの諸元 |

採点を生成と別ファイルにしているのは、**採点器を直したときに数時間分の生成を捨てずに
採点だけやり直せる**ようにするため。

## 実測 — 手元で回した結果

**このツールが何を出すのかを、実データで示す。**
測定の全文は [docs/measurements/2026-08-26-s9.md](docs/measurements/2026-08-26-s9.md) にある。

| | |
|---|---|
| 測定日 | 2026-08-26 / run `s9` |
| 機材 | Apple M4 Pro / macOS 26.5.2 / ollama `0.32.13` |
| 母数 | モデル **6** 本 × ケース **31** 件 × 反復 5 回 = 生成 **930** 件 |
| 量子化 | **6 本すべて `Q4_K_M`** |
| 識別力なしのケース | **0 件** |

**独立した観測は 8 次元すべてで 2 件以上ある。** ケースは 31 件あるが、
そのうち多くは**同じ問題の日本語版と英語版**なので、`31` は観測の数ではない
（[`task`](#task--ケースの数と観測の数は違う) で数えると 17 件）。

### 見つかったこと — 日本語で JSON を頼むと、キー名まで訳される

`name` / `age` / `occupation` をキーに持つ JSON を**日本語で**頼んだとき、
**6 モデル中 5 モデルがキー名を日本語に訳した**（seed 5 本すべての結果）。

| モデル | キー名を訳した生成 | seed 1000 の出力 |
|---|---|---|
| `llama3.2:1b-instruct-q4_K_M` | **5 / 5** | `{"名前":"田中一郎","年齢":"42歳","職業":"造船所の溶接工"}` |
| `llama3.2:3b` | **5 / 5** | `{"年齢":42,"職業": "溶接工", "名前":"田中一郎"}` |
| `qwen2.5:0.5b` | 4 / 5 | `{ "名前": "田中一郎", "年齢": 42, "職業": "造船所の溶接工" }` |
| `qwen2.5:1.5b` | **0 / 5** | `{ "name": "田中一郎", "age": 42, "occupation": "造船所の溶接工" }` |
| `qwen2.5:3b` | 1 / 5 | `{ "name": "田中一郎", "age": 42, "occupation": "造船所の溶接工" }` |
| `qwen2.5:7b` | **5 / 5** | `{ "名前": "田中一郎", "年齢": 42, "職業": "造船所の溶接工" }` |

**訳さないのは `qwen2.5:1.5b` だけ。** 値は正しく、**訳してはいけない識別子まで訳している。**

**これは「日本語が苦手」ではない。** `qwen2.5:7b` を例に取ると、
**同じ課題の英語版は 5/5 正解**（`ja_penalty` +1.000 = 最大）で、
**`code-gen` の日英差は ±0.000**。
**日本語そのものではなく、日本語 × 形式制約**で壊れている。

（英語版で満点を取ったのは 6 モデル中 4 本。`llama3.2:3b` は 0.80、`llama3.2:1b` は 0.40 で、
この 2 本は英語側でも落としている。）

**この結果は量子化を替えても動かなかった。** `llama3.2:1b` を `Q8_0` から `Q4_K_M` に
差し替えて測り直しても、**6 モデルの内訳は 5/5・5/5・4/5・0/5・1/5・5/5 のまま**だった。

**このケースに固有かもしれない。** 別の日本語 × 形式制約のケース（列挙値・配列の件数・真偽値）では、
`qwen2.5:7b` が 5/5 正解で `qwen2.5:1.5b` が 3/5 だった。**勝敗がケースごとに入れ替わる。**

### 次元プロファイル

`z` は**ケース単位の残差を次元内で標準化した値**。ケースの難易度が相殺されるので次元をまたいで比較できる。
**次元ごとの相対的な位置**であって、点数ではない。

**合計欄は無い。** 次元をまたいだ平均は出さない — 尺度の違うものを平均すると意味が壊れる。
行は次元順、列はモデル名の辞書順で、**どちらもスコア順ではない**。

| 次元 | `llama3.2:1b-instruct-q4_K_M` | `llama3.2:3b` | `qwen2.5:0.5b` | `qwen2.5:1.5b` | `qwen2.5:3b` | `qwen2.5:7b` |
|---|---|---|---|---|---|---|
| `code-fix` | -0.44σ | +0.55σ | -1.75σ | +0.22σ | +0.71σ | +0.71σ |
| `code-gen` | -0.94σ | +0.54σ | -1.53σ | +0.40σ | +0.69σ | +0.84σ |
| `code-read` | -0.81σ | +0.27σ | -0.81σ | -0.27σ | +0.27σ | +1.35σ |
| `extract` | -1.62σ | +0.25σ | -0.18σ | +0.09σ | +0.84σ | +0.62σ |
| `ideate` | -0.31σ | -0.07σ | -0.60σ | +0.29σ | -0.03σ | +0.71σ |
| `instruct` | -1.38σ | +0.22σ | +0.07σ | +0.80σ | -0.07σ | +0.36σ |
| `longctx` | +0.42σ | +0.42σ | -2.11σ | +0.42σ | +0.42σ | +0.42σ |
| `reason` | -0.35σ | -0.63σ | -0.49σ | -0.63σ | +0.63σ | +1.47σ |

**サイズ順に並んでいない。** `instruct` では `qwen2.5:1.5b`（+0.80σ）が `qwen2.5:7b`（+0.36σ）を上回り、
`extract` では `qwen2.5:3b`（+0.84σ）が `qwen2.5:7b`（+0.62σ）を上回る。
**総合スコアで並べれば消える差**が、ここでは残る。

### `ja_penalty` — 同じ課題の日英差分

`en − ja`。**正の値が「日本語で聞くと落ちる」。** 対訳ペアの両側が揃ったケースだけが対象。

| 次元 | `llama3.2:1b-instruct-q4_K_M` | `llama3.2:3b` | `qwen2.5:0.5b` | `qwen2.5:1.5b` | `qwen2.5:3b` | `qwen2.5:7b` |
|---|---|---|---|---|---|---|
| `code-fix` | +0.500 | -0.100 | +0.100 | +0.100 | +0.000 | +0.000 |
| `code-gen` | -0.200 | +0.000 | +0.200 | -0.100 | -0.100 | +0.000 |
| `code-read` | +0.000 | +0.000 | +0.000 | -0.500 | +0.000 | +0.000 |
| `extract` | -0.220 | -0.280 | +0.160 | -0.020 | -0.140 | +0.020 |
| `ideate` | +0.110 | +0.083 | +0.112 | +0.055 | +0.030 | +0.065 |
| `instruct` | +0.300 | +0.400 | +0.500 | +0.200 | -0.200 | +0.500 |
| `longctx` | — | — | — | — | — | — |
| `reason` | +0.000 | +0.000 | -0.100 | +0.000 | -0.100 | -0.500 |

`—` は**対象外**（対訳ペアが無い）。**0 と書かない** — 0 は「差が無い」であって「測っていない」ではない。

**`instruct` は 6 本中 5 本が正の値**（`qwen2.5:3b` だけ −0.200）。
形式制約つきの依頼は、日本語で聞くと落ちる側に揃っている。

> **前の測定にあった `code-read` の落差は消えた。**
> ケースが 1 種類だったとき、`llama3.2` の 2 本は `+1.000`（最大）を示していた
> — 英語では行番号を正解し、日本語では外していた。
> **2 種類目の問題を足したら、`llama3.2:3b` は新しい問題で符号が逆（−1.000）になり、
> 次元としては ±0.000 に戻った。**
>
> これは測定の誤りが直ったのではない。**1 種類のケースで見えていたものが、
> 次元の性質ではなくそのケースの性質だった**ということ。
> 下の[安定性の表](#結論の安定性--ケースを-1-件抜くとどうなるか)は、
> ケースを足す前の時点で `code-read` を**最も不安定な次元の 1 つ**として示していた。

### 結論の安定性 — ケースを 1 件抜くとどうなるか

**`qb stability` の出力。** 観測を 1 件ずつ抜いて集計し直し、`z` がどこまで動くかを見る。
**新しい生成はしない** — 既存の採点行を読み直すだけ。

**抜く単位は問題の種類（`task`）で、ケースではない。** 同じ問題の日本語版だけを抜いても
英語版が残るので、その観測は消えない。消えないものを抜いても
「この観測が無かったらどうなるか」には答えられない。

| 次元 | 独立な観測 | 1 件抜きの最大幅 | 符号が定まらないモデル |
|---|---|---|---|
| `code-fix` | 2 | 1.17 | 1 |
| `code-gen` | 2 | 1.01 | 0 |
| `code-read` | 2 | 1.59 | 3 |
| `extract` | 2 | 0.93 | 2 |
| `ideate` | 2 | 3.29 | 3 |
| `instruct` | 2 | 1.38 | 3 |
| `longctx` | 3 | 0.11 | 0 |
| `reason` | 2 | 1.34 | 2 |

**「符号が定まらない」は誤りの印ではない。** `z` が 0 付近のモデルは、
1 件抜けば当然どちらにも振れる。**問題になるのは `z` が 0 から離れているのに振れるとき**で、
この測定では **0 件**（`|z| >= 1.0` のモデルはすべて符号が保たれた）。

**観測数の違う次元の幅は直接比べられない。** 観測が 2 件の次元では 1 件抜くと半分が消えるので、
幅は構造的に大きく出る。観測 3 件の `longctx` が 0.11 なのはそのぶんを含む。

**`ideate` が突出している（3.29）。** `ideate` のスコアは 3 つの積で、
実測値が 0.06〜0.29 の狭い帯に収まる（[理由](#ideate--発想ではなく制約内多様性を測る)）。
帯が狭いぶん σ も小さく、**わずかな差が大きな `z` になる。**
順位を主張できる状態ではない。

### 量子化を落とすと何が起きたか

`llama3.2:1b` を `Q8_0` から `Q4_K_M` に差し替えて測り直した。
**モデルもケースも seed も同じで、量子化だけが違う。**

両方の測定にあるケースは 19 件で、**うち 12 件で値が動いた**。
**8 件が下がり、4 件が上がった。**

**合計は出さない。** 次元をまたいだ和は尺度の違うものを足すことになる
（この節を書いたとき実際に合計欄を作ってしまい、`tools/check-readme.py` に止められた）。

| ケース | `Q8_0` | `Q4_K_M` | 差 |
|---|---|---|---|
| `code-read-off-by-one-en` | 1.00 | 0.00 | **-1.00** |
| `code-gen-two-sum-en` | 0.60 | 0.20 | -0.40 |
| `code-fix-median-ja` | 1.00 | 0.60 | -0.40 |
| `instruct-tags-en` | 0.60 | 0.20 | -0.40 |
| `extract-vet-ja` | 0.68 | 0.44 | -0.24 |
| `instruct-tags-ja` | 0.20 | 0.00 | -0.20 |
| `reason-change-en` | 0.00 | 0.20 | +0.20 |
| `reason-change-ja` | 0.00 | 0.20 | +0.20 |
| `code-fix-median-en` | 0.80 | 1.00 | +0.20 |

（差が 0.10 未満の 3 件は省いた。）

**これは量子化一般の話ではない。** 1 モデル・19 ケース・5 反復・1 台の Mac での観測で、
`temperature` は 0.8 なので、重みが変われば同じ seed でも生成の道筋は変わる。
**それでも、量子化を揃えずに「1b と 3b の差」を語ると何を見ているか分からない**ことは示している。

### この数字をどう読むか

- **モデルの能力の測定ではない。** 4bit 量子化の重みを 1 台の Mac で、同梱ケースだけで走らせた結果
- **ケースを変えれば結論が変わる。** この README でも実際に 2 回起きた —
  `instruct` の問題を 1 種類から 2 種類にしたとき、`code-read` の日英差が消えたとき。
  **どちらも `qb stability` が事前に不安定だと示していた次元**だった
- **モデル 6 本では σ の推定が甘い。** 足すほど安定する
- **`ideate` の順位は主張できない。** 実測値が狭い帯に収まるので、
  1 件抜くと `z` が 1.57 動く（他の次元は 1.0 未満）
- **同じ数字にはならない。** digest・ollama のバージョン・機材が変われば動く。
  **量子化を替えるだけで 19 ケース中 12 件が動いた**


## レポート — 順位表ではなく輪郭

```sh
uv run qb report --run main          # reports/<run>/report.md と compare.md
uv run qb report --run main --all-seeds
```

**1 つの run だけを読む。** 残差はケース内でモデル間の平均を引くので、
run をまたぐと**引き算の相手が別の測定条件で測られたもの**になる。
同じ run の中でモデルの digest や ollama のバージョンが混ざっていたら**拒否する**。

`report.md` に出るもの:

| 表 | 中身 |
|---|---|
| 次元プロファイル | `z`（ケース単位の残差を次元内で標準化）/ 絶対スコア / **反復ばらつき** |
| ケース単位のスコア | **識別力の無いケースを理由つきで名指しする**（下記） |
| `ja_penalty` | 対訳ペアの日英差分。ペアが無い次元は `—` |
| 失敗型の分布 | 分母は**適用されたケース数**。候補階層は別表 |
| 性能 | tok/s（総和ベース）・TTFT・load（中央値） |

**全モデルが同じ点を取ったケースは集計から外す。** 残差が全部 0 で情報を持たないため。
外した件数だけでなく **`ceiling`（全員満点＝ケースが緩い）と
`floor`（全員 0 点＝難しすぎるか採点器が壊れている）を区別して**出す。次の手が違うから。

**`z` に `!` が付いていたら、その次元は識別力のあるケースが 1 件しかない。**
その 1 ケースで決まっているという意味で、消さずに印を付けている。

`compare.md` は**同一 seed の生出力を並べたもの**。機械が付けた失敗型は候補にすぎず、
`ideate` の「発想の質」に至っては機械では測っていない。**最終判断はここを読んで人が行う。**

## 設計の要点

**なぜこの測り方なのかを、ここで完結させておく。**

コードとケースのコメントに `FLB-QB-001 §12.9` のような参照が出てくる。
**これは設計文書の節番号で、その文書は公開していない。**
棄却した案・独立レビューの指摘とその再現・実測のログが入っていて、
**読むのに必要なものはこの節と各コメント本文に書いてある**（節番号を辿る必要はない）。

**スコアはケース単位の残差で出す。** 絶対点だと、全モデルが落とす難しいケースが
「そのモデルの弱点」に見えてしまう。ケースごとに全モデルの平均を引くことで、
**ケースの難易度ではなくモデル間の差**が残る。だから**モデルを足すほど安定する**。

**失敗の型は、判定の固さで 3 階層に分ける。**

| 階層 | 中身 | 扱い |
|---|---|---|
| hard | `truncated` など、API の応答から一意に決まるもの | 主表に出す |
| declared | ケース YAML が判定手続きを宣言したものだけ | 宣言のあるケースだけが母数 |
| candidate | 閾値で決まるもの（反復率など） | 参考。主表に出さない |

**固いものだけを主表に出す。** 判定手続きの無い型を一律に適用すると、
**モデルの癖ではなく判定器の癖**を測ることになる。

**`pass@1` は不偏推定量の k=1 として計算する。** 素朴な `1 − (1 − c/n)^k` は
一貫して過小評価する（n=20, k=5, c=6 で 0.8709 対 0.8319、**3.89 ポイント**）。
式を 2 本持つと片方だけ直したときに静かにずれるので、**実装は不偏推定量 1 本だけ持つ**。

**生成コードは `sandbox-exec` で隔離する。`code-gen` は macOS 専用。**
**起動時に陰性カナリア 9 本 + 陽性対照を回して、隔離が生きているかを毎回自己診断する** —
1 本でも**期待どおりでなければ**コード実行を拒否する。
陰性カナリアは「失敗すれば合格」ではなく、**`EPERM` / `EACCES` を名指しで期待する**
（対象が存在しないだけの `ENOENT` は不合格）。**失敗の理由を見ないと、
対象が無い機械では境界をすべて外しても合格してしまう。**

**陽性対照を置くのは、陰性だけでは「全部落ちる」壊れ方に気づけないから。**
隔離が過剰に厳しくなる方向に壊れると、陰性カナリアは全部「期待どおり失敗」して合格を出し、
**全モデルが 0 点になったものが「このモデル群はコードが書けない」というプロファイルとして出る。**
参照解が自分のテストを通ることを毎回確かめれば、これは原理的に防げる。

## 何が残っているか

**ステータス行だけだと「何が動くか」は分かっても「あと何が残っているか」が分からない。**

**独立した観測が次元あたり 2〜3 件しかない。** 同梱ケースは 31 件あるが、
多くは同じ問題の日英版なので、[`task`](#task--ケースの数と観測の数は違う) で数えると 17 件。
**`qb stability` はこの少なさが結論に効いているかを数字にする**が、
**測れるようになるだけで、増えるわけではない。**

**同梱ケースだけで結論を出さない。** 実際、問題を 1 種類から 2 種類に増やしただけで
`instruct` は勝敗が入れ替わり、`code-read` は日英差が消えた。
ケースを足すのは利用者側でもできる（[ケースの書き方](#ケースの書き方)）。

| 残っているもの | 状態 |
|---|---|
| 独立した観測を増やす | 次元あたり 2〜3 件。`longctx` の 3 件だけが安定域（幅 0.11） |
| 別のモデルファミリを足す | 2 ファミリ 6 本。σ の推定はまだ甘い |
| `ideate` の帯の狭さ | スコアが 0.06〜0.29 に収まり、わずかな差が大きな `z` になる |

**測れていないものもある。**

- **モデルが 6 本・2 ファミリ**なので σ の推定はまだ小さい。足すほど安定する
- **`exec_timeout` が実データで出ていない。** 打ち切りの配線は検証済みだが、
  非停止を誘う課題を 4 通り・24 試行試して 1 件も起きなかった。
  **小型モデルは非停止コードよりも例外を出す**（`exec_error` は実際に出ている）
- **`ideate` の脱線判定の偽陽性率を測っていない。** 分離できていないことは分かっているが、
  どれだけ誤除外しているかは、ラベルを付けないと出せない。
  **ラベルを付けるのが実装者本人になる**ので、その測定はバイアスで汚れる
