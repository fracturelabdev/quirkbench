# quirkbench

**ローカル LLM の「癖」を測る。** 総合スコアで順位をつけるのではなく、
**そのモデルが何を得意とし、何を苦手とし、どう失敗するか**の輪郭を描く。

「発想や提案は良いが、コードは弱い」— そういう傾向を、手元のモデルで、自分の機材で測る。

対象は **Ollama で動くモデルのみ**。これは制約ではなく前提条件で、
課金もレート制限も無いからこそ**同じ問題を seed を変えて何度も回し、
ばらつきそのものを癖として測れる**。

> **ステータス: 開発中（v0.1.0.dev0）。** 生成・再開、`instruct`（形式検証）・
> `code-gen`（サンドボックス実行）・`ideate`（埋め込みによる代理指標）の採点、
> **プロファイル表と比較ビューの出力**までが動く。他の 5 次元の採点器は未実装。

## 測らないもの

**先に書く。ここを誤解したまま数字を読まれるのが一番まずい。**

- **「発想の質」は測っていない。** `ideate` 次元が出すのは
  **制約内多様性 (constrained diversity)** — 指定件数を守ったか、お題から外れていないか、
  想定観点をどれだけ含むか、案同士がどれだけ重複していないか。
  **「良いアイデアかどうか」は測れない。** 生の出力を全件保存して人が読めるようにしてあるので、
  質の判断はそちらで行う。
  スコアは `valid_rate × coverage × diversity` の**乗算**で、どれか 1 つが 0 なら 0 になる —
  支離滅裂な出力ほど案同士が散らばるので、多様性だけを見ると**壊れたモデルが最高得点を取る**
- **LLM に採点させない。** 手元で動く最大級のモデルでも、被験モデルと同程度かそれ以下の能力しかない。
  同じモデルファミリなら誤差が相関し、自分に似た出力を高く評価する
- **他人の環境の再現ではない。** 量子化・`num_ctx`・マシンの負荷で数字は動く。
  ここで出るのは**あなたの手元での**プロファイルであって、モデルの絶対的な性能ではない

## 分かっている限界

**設計上の限界を先に書く。** まだ実装していない機構の限界には `(未実装)` を付けてある —
限界だけ読んで「もう動く」と思われるのを避けるため。実装状況はステータス行を見てほしい。

- **モデル数が少ないとプロファイルが不安定になる。** `(未実装)` スコアは
  「ケースごとに全モデルの平均を引いた残差」で出す設計なので、比較対象が少ないほど推定が甘くなる。
  同じファミリのモデルばかりだと誤差も相関する。**モデルを足すほど安定する**
- **生成コードのメモリ使用量は制限できない。** macOS では
  `RLIMIT_AS` / `RLIMIT_DATA` / `RLIMIT_STACK` のいずれも設定できず、Python が
  `ValueError: current limit exceeds maximum limit` を投げる（この Mac で実測）。
  CPU 時間と実時間の二重で止める設計だが、**メモリ暴走に対する上限は無い**
- **生成コードが非決定的だと、判定の再現性を保証できない。** 時刻に依存する、
  浮動小数の演算順序に依存するコードは、実行のたびに通ったり落ちたりしうる。
  実行結果はコード内容単位でキャッシュするので**初回の判定が安定して返る**が、
  それは**誤っていても安定する**という意味でもある。二重実行による検出は入れていない
  （全ケースのコストが 2 倍になる）
- **`ideate` の脱線判定は、短い固有名詞で誤爆する。** 案とお題の埋め込み類似度で
  足切りしているが、実測で**良質な店名 `すずらん亭`（0.3196）が、無関係な出力
  `塾の音のすばやさ`（0.3261）より低く**出た。分離できていない（閾値 0.35）。
  誤爆で落ちたぶんは `valid_rate` と `valid_rate_morph`（足切り前）の差として
  `scores.jsonl` に残るので、**どれだけ削られたかは後から読める**。
  現状 **7b の `ideate` は過小評価**されている
- **`ideate` の絶対値は他の次元と直接比べられない。** 多様性がまともな出力でも 0.5 前後なので、
  合成スコアは 0.55 程度で頭打ちになる。`instruct` の 0〜1 とは尺度が違う
- **次元あたりのケースが少ないと、「次元に弱い」と「そのケースに弱い」を分けられない。**
  `z` は識別力のあるケースだけから計算するので、そのケースが 1 件しかなければ
  z はその 1 件で決まる。**`qb report` は該当する次元の z に `!` を付ける**が、
  分けられるようになるわけではない。**ケースを足すしかない**
- **計測中に他のプロセスが GPU やディスクを使うと数字が汚れる。** 特に `load_duration` に効く
- **仮名の無い短い日本語は言語判定できない。** 「珈琲小径」のような全漢字の店名を並べると
  `unknown` になり、`wrong_language` / `zh_leak` の母数から外れる。
  **判定不能を「別言語だった」と数えない**ためだが、そのぶん日本語運用の母数は減る

## 必要なもの

- Python 3.11 以上と [uv](https://docs.astral.sh/uv/)
- [Ollama](https://ollama.com/) が動いていること（`ollama serve`）
- 測りたいモデルが `ollama pull` 済みであること
- `ideate` 次元を採点するなら **埋め込みモデル**も要る（既定 `bge-m3`）

```sh
ollama pull bge-m3
```

```sh
uv sync
```

## 使い方

```sh
# 生成を実行する
uv run qb run --models qwen2.5:0.5b,qwen2.5:1.5b --repeats 5

# 進捗を見る
uv run qb status
```

**中断してよい。** `Ctrl-C` で止めても、同じ `--run` 名で再実行すれば続きから再開する。
全次元を複数モデルで回すと数時間かかるので、そういう作り方にしてある。

```sh
# 次元やケースで絞る
uv run qb run --models qwen2.5:7b --dims instruct,ideate
uv run qb run --models qwen2.5:7b --ids instruct-json-profile-ja
```

採点は生成と別のコマンドに分けてある。**採点は追記のみで、生成を書き換えない。**
期待値や schema を直したら `qb score` をもう一度回せばよく、数時間かけた生成は残る。

```sh
# プロファイル表と比較ビューを出す
uv run qb report --run main

# ケース定義のゲート（粒度・timeout・参照解）
uv run qb lint-cases

# 生成済みの応答を採点する
uv run qb score --run main

# 埋め込みモデルを替える（ideate 次元でのみ使う）
uv run qb score --run main --embed-model nomic-embed-text
```

## 開発

```sh
uv run pytest -q                       # テスト
uv run pytest --cov=src/quirkbench     # カバレッジ
uv run ruff check src tests tools      # lint
uv run ruff format src tests tools     # 整形
uv run mypy                            # 型
uv run python tools/mutate.py          # ミューテーション
```

これらは `.github/workflows/checks.yml` で機械的に回る。**手で叩く前提の検査は、
やったことがあるだけでいずれ静かに腐る** — 実際このリポジトリでも、型チェックを
一度も掛けていなかったことが後から見つかった。ollama は CI に無いので、
回るのは生成を伴わない検査だけ。実モデルでの計測は手元で行う。

`tools/mutate.py` は**安全策を 1 つずつ無効化して、テストが落ちることを確かめる**。
カバレッジは「その行を通ったか」しか見ないので、ガードが実際に呼ばれているかは別に測る。
実際、行カバレッジ 100% のファイルで 1 件のガードが無防備だったことがある。
**全部落ちるのが正常**で、生き残りが出たらテストを足すか、そのガードが冗長なら消す。

## ケースの書き方

ケースは `cases/<次元>/*.yaml` に宣言的に置く。コードには埋めない。

```yaml
id: instruct-json-profile-ja
dim: instruct
lang: ja
pair: instruct-json-profile-en   # 対訳。日英の差分から「日本語だと落ちるか」を出す

prompt: |
  次の人物紹介から、名前・年齢・職業を抜き出して JSON で出力してください。
  ...

options:
  num_predict: 256

failure:            # どの失敗型を適用するかの宣言。書かれていない型は判定しない
  format: json
  extract: fenced_or_first_object
  language: none    # JSON は言語を持たないので言語判定を適用しない
  min_tokens: 4

score:
  kind: json_schema
  schema: {...}
  expect:           # schema を満たしたうえで値まで合っているか（部分点）
    name: 田中一郎
    age: 42
```

**`failure` に書いていない型は集計の母数に入らない。** これは意図的で、
判定手続きの無い型を一律に適用すると、**モデルの癖ではなく判定器の癖**を測ることになる。

**ケースは読み込み時に検証され、通らないものは起動時に落ちる。** たとえば
`failure.max_tokens` に `options.num_predict` 以上の値を書くと拒否される —
先に `truncated` になるので `overlong` が原理的に発火せず、**母数だけ増えて分子が常に 0** になる。
長さ制約は `max_chars` で書くか `num_predict` を上げる。
（この検証は、同梱ケース 3 件すべてがこの誤りを踏んでいたのを見つけて足した）

## `code-gen` — 生成コードを実行して測る

**`code-gen` 次元は macOS 専用**（`sandbox-exec` が要る）。スコアは **0 か 1**（all-or-nothing）で、
反復の平均が `pass@1` になる。

```sh
uv run qb run   --models qwen2.5:1.5b,qwen2.5:7b --dims code-gen --run s3
uv run qb score --run s3 --dims code-gen
```

採点のたびに**隔離が生きているかを自己診断**し、1 本でも期待どおりでなければ**採点を拒否**する。
さらに**参照解が自分のテストを通ることをケースごとに確かめる**（陽性対照）— 陰性カナリアだけだと、
隔離が過剰に厳しくなる方向に壊れたときに**全モデルが 0 点になったものを
「このモデル群はコードが書けない」というプロファイルとして出してしまう**。

実行結果は `exec_cache.jsonl` にコード内容単位でキャッシュされる。
**同じコードが別の生成に現れるのは常態**で、手元の実測では 40 生成のうち実行が必要だったのは 24 回だった。
**採点をやり直してもサンドボックスは起動しない** — 起動するのはコードかテストか実行環境が変わったときだけ。

## `ideate` — 「発想」ではなく制約内多様性を測る

**採点に埋め込みモデルが要る**（既定 `bge-m3`）。スコアは 3 つの積で出す。

```
ideate = valid_rate × coverage × diversity
```

| 因子 | 中身 |
|---|---|
| `valid_rate` | 案として成立した件数 ÷ **要求件数**。産出件数で割らない — 1 案だけ返して満点が取れてしまう |
| `coverage` | 想定観点のグループをいくつ含んだか |
| `diversity` | 案同士の埋め込み距離の平均。1 案以下なら 0 |

**成立判定は 2 段。** 第 1 段は形態（長さ・文字種）で決定的。第 2 段はお題との埋め込み類似度で、
**こちらは誤爆する**（「分かっている限界」参照）。第 1 段だけの値も `valid_rate_morph` として
併記するので、**第 2 段がどれだけ削ったかは後から読める**。

```sh
uv run qb run   --models qwen2.5:1.5b,qwen2.5:7b --dims ideate --run s4
uv run qb score --run s4 --dims ideate
```

埋め込みは `embeddings.jsonl` に本文単位でキャッシュされる。
**採点をやり直しても再計算しない** — 手元の実測では、20 生成を採点し直したとき
埋め込みの計算は **0 本**（キャッシュヒット 108 本）だった。

## 出力

`runs/<run 名>/` に追記される。**一度書いた生成は書き換えない。**

| ファイル | 中身 |
|---|---|
| `generations.jsonl` | 生成 1 件 1 行。生の応答と所要時間。**不変** |
| `prompts.jsonl` | プロンプト本文（重複排除） |
| `scores.jsonl` | 採点結果。再採点は追記のみで、過去の採点も残る |
| `exec_cache.jsonl` | 生成コードの実行結果。コード内容単位（`code-gen` のみ） |
| `embeddings.jsonl` | 埋め込みベクトル。本文単位（`ideate` のみ・1 行あたり約 14KB） |
| `reports/<run>/report.md` | プロファイル表（`qb report` が出す） |
| `reports/<run>/compare.md` | 同一 seed の生出力を並べた比較ビュー |
| `meta.json` | モデルの digest、Ollama のバージョン、マシンの諸元 |

採点を生成と別ファイルにしているのは、**採点器を直したときに数時間分の生成を捨てずに
採点だけやり直せる**ようにするため。

## レポート — 順位表ではなく輪郭

```sh
uv run qb report --run main          # reports/<run>/report.md と compare.md
uv run qb report --run main --all-seeds
```

**1 つの run だけを読む。** 残差はケース内でモデル間の平均を引くので、
run をまたぐと**引き算の相手が別の測定条件で測られたもの**になる。
同じ run の中でモデルの digest や ollama のバージョンが混ざっていたら**拒否する**。

`report.md` に出るもの:

| 表 | 中身 |
|---|---|
| 次元プロファイル | `z`（ケース単位の残差を次元内で標準化）/ 絶対スコア / **反復ばらつき** |
| ケース単位のスコア | **識別力の無いケースを理由つきで名指しする**（下記） |
| `ja_penalty` | 対訳ペアの日英差分。ペアが無い次元は `—` |
| 失敗型の分布 | 分母は**適用されたケース数**。候補階層は別表 |
| 性能 | tok/s（総和ベース）・TTFT・load（中央値） |

**全モデルが同じ点を取ったケースは集計から外す。** 残差が全部 0 で情報を持たないため。
外した件数だけでなく **`ceiling`（全員満点＝ケースが緩い）と
`floor`（全員 0 点＝難しすぎるか採点器が壊れている）を区別して**出す。次の手が違うから。

**`z` に `!` が付いていたら、その次元は識別力のあるケースが 1 件しかない。**
その 1 ケースで決まっているという意味で、消さずに印を付けている。

`compare.md` は**同一 seed の生出力を並べたもの**。機械が付けた失敗型は候補にすぎず、
`ideate` の「発想の質」に至っては機械では測っていない。**最終判断はここを読んで人が行う。**

## 設計の要点

**なぜこの測り方なのかを、ここで完結させておく。**
（判断に至るまでの記録 — 棄却した案、独立レビューの指摘とその再現 — は別に残しているが、
公開していない。**読むのに必要なものはこの節にある。**）

**スコアはケース単位の残差で出す。** 絶対点だと、全モデルが落とす難しいケースが
「そのモデルの弱点」に見えてしまう。ケースごとに全モデルの平均を引くことで、
**ケースの難易度ではなくモデル間の差**が残る。だから**モデルを足すほど安定する**。

**失敗の型は、判定の固さで 3 階層に分ける。**

| 階層 | 中身 | 扱い |
|---|---|---|
| hard | `truncated` など、API の応答から一意に決まるもの | 主表に出す |
| declared | ケース YAML が判定手続きを宣言したものだけ | 宣言のあるケースだけが母数 |
| candidate | 閾値で決まるもの（反復率など） | 参考。主表に出さない |

**固いものだけを主表に出す。** 判定手続きの無い型を一律に適用すると、
**モデルの癖ではなく判定器の癖**を測ることになる。

**`pass@1` は不偏推定量の k=1 として計算する。** 素朴な `1 − (1 − c/n)^k` は
一貫して過小評価する（n=20, k=5, c=6 で 0.8709 対 0.8319、**3.89 ポイント**）。
式を 2 本持つと片方だけ直したときに静かにずれるので、**実装は不偏推定量 1 本だけ持つ**。

**生成コードは `sandbox-exec` で隔離する。`code-gen` は macOS 専用。**
**起動時に陰性カナリア 9 本 + 陽性対照を回して、隔離が生きているかを毎回自己診断する** —
1 本でも**期待どおりでなければ**コード実行を拒否する。
陰性カナリアは「失敗すれば合格」ではなく、**`EPERM` / `EACCES` を名指しで期待する**
（対象が存在しないだけの `ENOENT` は不合格）。**失敗の理由を見ないと、
対象が無い機械では境界をすべて外しても合格してしまう。**

**陽性対照を置くのは、陰性だけでは「全部落ちる」壊れ方に気づけないから。**
隔離が過剰に厳しくなる方向に壊れると、陰性カナリアは全部「期待どおり失敗」して合格を出し、
**全モデルが 0 点になったものが「このモデル群はコードが書けない」というプロファイルとして出る。**
参照解が自分のテストを通ることを毎回確かめれば、これは原理的に防げる。

## 何が残っているか

**ステータス行だけだと「何が動くか」は分かっても「あと何が残っているか」が分からない。**

| 残っているもの | いつ |
|---|---|
| 残り 5 次元 | 次 |
| README に実データのプロファイルを載せる | 最後 |

**次元あたりのケースが足りない。** 手元の実測では、識別力のあるケースが
**1 件しかない次元が 2 つ**あった。そうなると
**「この次元に弱い」と「このケースに弱い」を分けられない**。
`qb report` はその次元の `z` に `!` を付けて知らせる。

**測れていないものもある。**

- **`exec_timeout` が実データで出ていない。** 打ち切りの配線は検証済みだが、
  手元の qwen2.5 4 サイズは同梱ケースで無限ループを書かなかった。
  非停止を誘うケースを足すまで、この型は「未観測」
- **モデルが 4 本・同一ファミリ**なので残差の推定が甘い。別ファミリを足すと安定する
- **`ideate` のケースが日本語 1 件だけ。** 対訳が無いので日英差分が出せない
